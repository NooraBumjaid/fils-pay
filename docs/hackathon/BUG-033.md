# BUG-033 — Concurrent refunds could exceed captured balance

**Severity:** Critical — duplicate financial reversal
**Area:** FP-300, payment concurrency

## Finding

Two requests with different idempotency keys could both read the same refunded total, pass validation, and call the acquirer concurrently. The per-key idempotency constraint did not serialize different keys for one transaction.

## Fix

Hold a PostgreSQL transaction-scoped session advisory lock keyed by transaction UUID through validation, acquirer call, and journal write. Each database phase remains transactional on the same checked-out session.

## Verification

Added and passed a database-backed race regression: two different keys each request 6,000 fils from a 10,000-fils capture; only one refund is accepted and only 6,000 fils are journaled. The focused refund service/route suite passes 23/23.
