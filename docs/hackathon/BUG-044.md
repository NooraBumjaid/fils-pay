# BUG-044: OTP guess limits were bypassable under concurrency and resend

**Severity:** Critical  
**Component:** merchant/admin authentication  
**Status:** Fixed and verified

## Evidence

Both OTP verify routes read `attempt_count`, checked it, and later incremented
it in a separate statement without a lock. Parallel requests could all pass
the same stale counter. The admin route's old comment claimed `FOR UPDATE`,
but its query did not take a row lock.

The merchant resend flow also issued a new challenge with the default zero
attempt count despite its comment claiming that prior guesses were carried
forward. Concurrent resend requests could both pass a cooldown check made
before the transaction and create multiple replacement challenges.

## Fix

Verification now locks the pending session and its current challenge in one
transaction, checks and increments the guess counter under those locks, and
consumes/promotes the challenge atomically. Reaching the configured limit
revokes the pending session. Merchant resend now takes the same session-then-
challenge lock order, checks the cooldown against the currently attached
challenge, and carries its attempt count into the replacement challenge.

## Regression coverage

- 25 parallel wrong codes against a merchant challenge stop at its configured
  maximum and leave the session unauthenticated.
- 25 parallel wrong codes against an admin challenge stop at its configured
  maximum and leave the session unauthenticated.
- A merchant challenge resend preserves a prior failed attempt, and two
  concurrent resends produce only one replacement challenge.

All 54 tests in `app.test.ts` and `routes/admin.test.ts` passed against the
isolated `fp300audit` Postgres database. `npm run typecheck` also passed.
